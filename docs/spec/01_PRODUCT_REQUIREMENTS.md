# 01. 产品需求与范围

## 1. 产品名称

- 中文：**校驿**
- 英文：**Campus Delivery Desk**
- 仓库：`campus-delivery-desk`

## 2. 使用场景

团队约 3～5 人，客户通过微信联系。客户不登录系统。

```text
微信接单
→ 录单员规范录入
→ 配送员接任务
→ 取件/取货
→ 配送
→ 拍照 + 放置位置
→ 录单员生成客户/代理凭证
→ 微信发送
→ 确认收款
→ 实时统计
```

系统部署在小主机，通过 HTTPS + 内网穿透访问。

## 3. 角色

### 管理员

拥有全部管理权限：账号、配置、订单、异常、人工调整、经营分析、工资计算、Excel、审计、图片、备份恢复、维护模式。

### 录单员

负责普通/代理录单、客户资料、异常处理、结算、图片生成、快速完成/补录、人工费用调整、查看有限经营数据。

### 配送员

负责开始/停止接单、选择当前业务类型、接任务、取件、配送、拍照、放置位置、转单、归拢、报告异常、查看个人统计。

## 4. 登录与账号

- 一人一号，管理员手工创建，无公开注册。
- 普通登录：先选角色，再从下拉列表选人员，输入随机口令。
- 管理员入口放在角落。
- 一个账号同一时间只允许一个活跃会话。
- 浏览器约每 30 秒心跳；租约约 150 秒无心跳视为过期。
- 已在线账号在其他浏览器登录时拒绝；旧租约 stale 后允许重新登录。
- 管理员可强制下线。
- 登录 Cookie 默认 30 天，但是否“当前在线”由活跃租约决定。
- 不做连续输错密码限流。

## 5. 客户与代理

### 5.1 普通客户

长期 Customer 档案允许不完整：

- 微信昵称/显示名；
- 收件人名称（文本，可用 `/` 分隔多个名称）；
- 手机尾号（文本，可用 `/` 分隔多个尾号）；
- 楼栋、楼层、房间；
- 长期备注。

首次建客户只要求最少必要信息；送上楼时楼栋/楼层/房间变为条件必填。

修改 Customer 只影响之后新订单，历史订单使用快照。

不实现客户合并。

### 5.2 代理单

V1 的代理体系仅用于快递业务。外卖、KFC、果蔬、跑腿、行李搬上楼不使用代理来源。

代理单采用独立结构：

```text
Agent（长期代理人）
→ ProxyBatch（一次代理推单/结算范围）
→ ProxyRecipient（本批次临时收件人）
→ Express Orders
```

ProxyRecipient 不进入正式客户库，下一次代理推单重新创建。

允许临时收件人名称非常灵活，例如 `15号楼#1`。系统应提供自动生成 `{楼栋}号楼#{序号}` 的能力。

每件代理快递必须绑定某个 ProxyRecipient，方便同一人的快递放在一堆、归拢和拍照。

整批代理单取消采用一次事务完成：仅 OPEN 批次且不存在已经实际取到、配送中或已送达的有效快递时允许；系统自动取消批次内仍处于 NEW/ASSIGNED 的未取件订单、释放相关未取件任务，并关闭因此变成“全部取消”的 ExpressRound，最后将批次置为 CANCELED。若已有 PICKED/DELIVERING/DELIVERED 快递则禁止整批取消，改为逐单取消仍未取件的订单，并对已拿到实物的订单走异常/人工处理。

代理单默认使用我方价格表，由代理人与我们结算。

## 6. 正式业务类型

### 6.1 快递代取

#### 大小与基础价

- 未知：价格待确认；
- 小件：2 元——不费吹灰之力；
- 中件：4 元——一只手可勉强拿起；
- 大件：6 元——一人费力抱起；
- 超大件：8 元——需两人抬举。

录单时允许 UNKNOWN。订单创建时保存当时完整的四档快递价格快照；最终配送员实际接触物件后确认大小，并按订单创建时对应档位价格计费。未确认大小不可最终结算。

#### 取件区域

- 南区；
- 北区；
- 校外。

选择校外时必须填写具体取件地点。校外多个站点距离较近，可以统一进入“校外路线”池。

取件信息统一叫“取件标识”，可为取件码、运单号或其他领取依据。

#### 特殊方向

校内取件后送到校外租房等地址：详细地址必填，并产生默认 +2 元/件费用项。

#### 配送模型

- 动态路线组批；
- 客户直送/加急；
- 物件级取件状态；
- 同客户多件归拢；
- 路线按取件区域 + 目的区域组织；
- 校外取件默认 +1 元/件。

### 6.2 校门口外卖代取

基础费 3 元/单。

必填：取餐区域（南门/北门/其他）、外卖识别信息、目标位置。OTHER 时具体地点必填。

外卖没有取餐码字段。

### 6.3 周四石湫肯德基代取

基础费 10 元/单。

必填：取餐地点、取餐码、目标位置。

默认开放日周四；其他日期录单时只提示，不绝对禁止。

### 6.4 果蔬/零食代购配送

配送费 5 元/单。

必填：取货地点、清单、目标位置。

商品购买金额线下人工解决，不进入系统账务。

### 6.5 跑腿送东西

独立业务，不与快递合并。基础建议价 3 元起。

必填：取货地点、送达地点、物品描述；大小可选未知/小/中/大/超大。

距离远、物品特殊等通过人工费用项加价，不做地图距离自动计价。

### 6.6 行李搬上楼

仅保留“搬上楼”，不实现复杂行李搬运。

- 小/中件：0.5 元/层/件；
- 大/超大件：1 元/层/件；
- 从 1 楼开始计算。

不支持加急。通常客户在现场，完成照片可选。

如果需要从某处先取行李再搬上楼，用备注描述，并在结算时添加额外费用项。

## 7. 加急规则（管理员可修改）

| 业务 | 默认加急费 | 单位 |
|---|---:|---|
| 快递 | +1 元 | 每件 |
| 外卖 | +2 元 | 每单 |
| KFC | +5 元 | 每单 |
| 果蔬零食 | +2 元 | 每单 |
| 跑腿送东西 | +2 元 | 每单 |
| 行李搬上楼 | 不支持 | - |

## 8. 特殊天气

特殊天气为低频人工费用项：结算时可勾选，默认 +2 元/一个收件归属的一次结算轮，管理员可改金额。普通客户按 Customer 当前结算轮计一次；代理快递按每个 ProxyRecipient 当前轮分别计一次。该费用项在 DRAFT 结算中创建并必须绑定当前 `settlement_id`；快递场景同时记录对应 `express_round_id`，不得仅凭 Customer/ProxyRecipient 在后续结算中重复拾取。

不接天气 API，不自动判断。

## 9. 多件快递优惠

只在单次快递结算轮次内可选应用，不跨轮累计，也不做每日累计。应用时创建绑定当前 `settlement_id` 与对应 `express_round_id` 的负 ChargeItem。

公式：

```text
max(本轮快递件数 - 5, 0) × 0.5 元
```

默认不自动应用；录单员结算时按实际情况勾选。

## 10. 统一费用项

所有价格变化必须形成独立费用项，包括基础费、校外费、校内送校外、加急、天气、上楼、客户自愿加价、手工增费、减免、多件优惠。

“客户自愿加价”100% 计入该费用项明确指定的 beneficiary courier 收益，作为强制归属收益；本轮只有一个最终配送员时可自动选择，多人时必须由录单员选择，需多人分配则拆成多条费用项。

## 11. 配送位置与照片

- 每个订单使用明确的 `requires_upstairs` 字段记录本单是否要求送上楼；客户地址中的楼层/房间不能替代该字段。
- 非送上楼默认放快递架/外卖架；最终位置必填。
- 位置使用快捷词 + 自由文本。
- 普通配送至少 1 张照片必填，推荐“近景 + 远景”。
- 远景可用画笔/圆圈/箭头标注物件所在位置，标记图为派生图。
- 第二张照片与标注均推荐但不强制。
- 行李搬上楼照片可选。

## 12. 归拢

快递使用显式 `ExpressRound` 表示“某个 Customer/ProxyRecipient 在某个 service_date 下的本轮快递”。所有 EXPRESS 订单的 `service_date` 必填，录单时默认当前本地日期；只有提前录未来快递时才修改。新快递优先加入同一收件归属、同一 service_date、状态仍为 OPEN 的 ExpressRound；上一轮关闭后，即使仍是同一天，新录入快递也进入下一轮。

自动归拢只包含已送达、未进入其他归拢、非上楼/当面交付、无 `OPEN && blocks_consolidation=true` 异常的快递。ExpressRound 内不存在 NEW/ASSIGNED/PICKED/DELIVERING 后按有效已送达数量处理：0 件（全部取消）直接 CLOSED；1 件无需归拢直接 CLOSED；至少 2 件时仅对符合条件的物件建立必要 ConsolidationRound，没有任何需要归拢的候选则直接 CLOSED；存在必要归拢时待其全部完成后 CLOSED。

默认归拢负责人为该轮相关成员中最后一个完成配送的配送员。归拢负责人后续调整使用独立的归拢改派动作，只改变 ConsolidationRound 负责人并记录审计，不改变已经完成订单的 Assignment。

录单员/管理员仍可对已送达的合格子集提前人工建立 ConsolidationRound；成员冻结后不能向该 ConsolidationRound 追加物件。

## 13. 结算与图片

- 不跨业务类型合并结算。
- 普通业务：按客户/本轮结算；快递的“本轮”以 ExpressRound 为边界。
- 代理单：每个 ProxyRecipient 生成一张可转发的客户凭证；“是否显示价格”默认开启。
- 代理人另外得到一张无照片的 ProxyBatch 汇总结算图。
- 代理人的下游售价不进入本系统。
- ChargeItem 是业务费用来源，错误费用项使用 VOIDED 逻辑作废，不物理删除。
- `build_settlement()` 创建 DRAFT 并用 SettlementOrder 固定本轮订单，但 DRAFT 阶段仍可编辑费用项，不立即生成 SettlementLine。
- 点击“生成有效结算凭证/进入待付款”时，系统把当前 ACTIVE ChargeItem 复制为不可变 SettlementLine，冻结应收金额，并将 Settlement 与其 Order 一并切到 WAITING_PAYMENT。
- DRAFT 或尚未真正付款的 WAITING_PAYMENT 账单可以 VOIDED 后重建；冻结后的 SettlementLine 不直接编辑。
- 生成图片 ≠ 已付款；收到钱后由录单员/管理员确认 SETTLED。
- 已确认付款后的误结算使用 REVERSED，保留原 Settlement/收益/图片历史；再次结算创建新记录。
- 普通客户结算图、ProxyRecipient 凭证和 Agent 汇总图同样属于图片生命周期管理对象，默认 30 天；结构化 Settlement/SettlementLine 永久保留，可在图片已清理后生成无原始配送照片的历史凭证。
- 不支持部分付款。

## 14. 工资

正式工资计算只使用已经完成客户/代理结算的净服务营业收入，待付款收入不进入可分配池。

工资计算器两种模式：

1. 按业务分成比例自动计算；
2. 管理员手工分配。

手工模式的可分配池为所选周期已完成客户/代理结算的净服务营业收入。具有强制收益归属的金额先锁定给对应成员，例如“客户自愿加价”100% 归费用项指定的 beneficiary courier；其余人工分配总额不得超过剩余可分配池。个人最终工资高于个人直接产生的普通配送收益时只警告，不阻止。

## 15. 经营分析

使用一个统一多维筛选式 Dashboard。可按时间、业务、成员、普通/代理、代理人、路线、快递大小、取件区域、目的区域、是否加急、上楼、天气、异常、退款、费用项等筛选。

V1 直接实时聚合事实表，不建立每日统计真值表。

## 16. 客户端

- 管理员/录单员：同时支持 Windows 宽屏布局和 Android 手机布局。
- 配送员：只设计移动端工作流；电脑打开时仍展示居中的手机式卡片布局。
- 不依赖 User-Agent 作为唯一布局判断，主要使用响应式断点/触控能力。
- 提供至少 4 套主题：亮色、暗色、暖色、清爽蓝/青色。
- 使用 Responsive Web + PWA，不开发原生 APK/EXE。

## 17. 明确不做

- 客户自助注册/下单；
- 在线支付；
- 站内通知、Push、微信自动消息；
- 客户合并；
- 地图导航/GPS；
- 真离线业务；
- 复杂行李搬运；
- 日终收工/每日优惠返还系统。
